# 단계 2 — 조사 대상 결정: 대체·가정·누락·맥락 상실 제거

> 변경 기록 번호: C2, C3, C4 · 전체 기록은 `과제1_코드변경기록.md` · 목차는 [README](README.md)

## 1. 문제 — 무엇이, 왜, 어떤 영향이 있었나
개선 전에는 "어느 시스템을 조사할지"를 모델과 `auth-service` 하드코딩 폴백에 맡겼고, 실측에서 네 가지로 어긋났다.

| 번호 | 입력 | Before 결과 |
|---|---|---|
| B2 | `billing-service 응답 지연을 진단해주세요` (미등록) | 조용히 **auth-service로 대체**해 엉뚱한 수치를 답함 (42.1s) |
| B3 | `로그인이 너무 느려요` (시스템 미언급) | auth-service로 **가정**, 답변에 가정 표시 없음 (43.9s) |
| B6 | `web-01 CPU 급증, auth-service 커넥션 풀도 같이 확인해줘` | **web-01만** 조사, auth-service 누락 (40.7s) |
| B7 | (앞 질문 payments-service) `그 시스템 메모리는 어때?` | 이전 대화를 쓰지 않고 **auth-service** 조사 |

**원인**: ① `_extract_system_name`이 못 찾으면 `auth-service` 반환 ② 모델이 만든 계획의 research task를 검증 없이 사용 ③ 대화 이력을 대상 결정에 쓰지 않음.
**영향**: 사용자가 요청하지 않은 시스템의 수치를 근거로 장애 진단이 나간다. 사용자는 대체됐다는 사실조차 모른다.

## 3. Before 코드 (개선 전 원본)

**원본 `agent/graph.py` 40~47줄 (`_extract_system_name`)**

```python
def _extract_system_name(query: str) -> str:
    """정규식 대신 실제 KNOWN_SYSTEMS 멤버십 매칭 — MCP Prompt(incident_analysis_
    prompt)의 system_name은 "시스템: X" 한 줄짜리 컨텍스트라 항상 정해진 이름
    중 하나로만 고정한다(여러 개 언급돼도 join하지 않음 — 실제 조사 대상 목록은
    이후 plan()의 tasks가 별도로 결정). 쿼리에서 가장 먼저 등장하는 시스템을
    고르고, 하나도 안 걸리면 가장 흔한 사례인 auth-service로 폴백."""
    matches = [(query.index(s), s) for s in KNOWN_SYSTEMS if s in query]
    return min(matches)[1] if matches else "auth-service"
```

**원본 `agent/graph.py` 101~119줄 (`plan_node`)**

```python
@traceable(name="plan_node")
async def plan_node(state: AgentState, deps: SupervisorDeps) -> dict:
    """Wave 4 — Plan/Task 분해. Wave 2의 MCP Prompt가 표준 절차를 깔아준다.

    resource와 마찬가지로 이름을 어느 서버가 들고 있는지 미리 가정하지 않고,
    find_prompt()로 연결된 서버들을 먼저 조회해 찾은 뒤에만 get_prompt를 보낸다."""
    prompt_server = await deps.mcp.find_prompt("incident_analysis_prompt")
    procedure = await deps.mcp.get_prompt(
        "incident_analysis_prompt",
        {"system_name": _extract_system_name(state["query"]), "symptom": state["query"]},
        server=prompt_server,
    )
    result, usage = deps.fast_llm.plan(state["query"], procedure)
    targets = [t["target"] for t in result["tasks"]
               if t["agent"] == "research" and t.get("target")]
    event = {"type": "PlanCreated", "task_count": len(result["tasks"]),
             "targets": targets}
    return {"tasks": result["tasks"], "needs_analysis": result["needs_analysis"],
            "cost_usd": _cost(state, usage), "events": state["events"] + [event]}
```

## 4. After 코드 (현재)

**현재 `agent/targets.py` 75~89줄 (`resolve_targets`)**

```python
def resolve_targets(query: str, history: list[dict] | None,
                    known: set[str]) -> TargetResolution:
    # 결정 순서(위에서부터 먼저 해당하는 것):
    #   질문에 등록 시스템 있음 → 전부 조사 / 미등록만 있음 → 조회 불가 / 지시어+이력 → 이전 시스템 /
    #   그 외 → 대상 없음(되묻기)
    mentioned = find_known(query, known)
    unregistered = find_unregistered(query, known)
    if mentioned:                       # B6: 언급된 등록 시스템은 전부 조사
        return TargetResolution(mentioned, unregistered, "query")
    if unregistered:                    # B2: 미등록은 대체하지 않고 조회 불가로 처리
        return TargetResolution([], unregistered, "none")
    last = last_system_from_history(history, known)
    if last:                            # B7: 후속 질문은 이전 대화의 시스템 (답변에 표시)
        return TargetResolution([last], [], "history")
    return TargetResolution([], [], "none")   # B3: 가정하지 않고 되묻기
```

**현재 `agent/targets.py` 92~110줄 (`apply_targets`)**

```python
def apply_targets(tasks: list[dict], targets: list[str]) -> list[dict]:
    """모델이 만든 계획의 모니터링 task를 targets와 일치시킨다.
    빠진 시스템은 추가하고, targets에 없는 시스템(대체·하드코딩된 것)은 제거한다.
    research 외 task(analysis 등)는 그대로 둔다."""
    # 1) 모델이 만든 모니터링 task를 대상 이름으로 찾아 둔다 (재사용하려고)
    by_target = {t["target"]: t for t in tasks
                 if t.get("agent") == "research" and t.get("kind") == "monitoring"}
    # 2) targets 순서대로 task를 새로 구성: 모델이 이미 만든 것은 재사용, 빠진 것은 새로 추가.
    #    targets에 없는 대상(예: 모델이 끼워 넣은 auth-service)은 여기서 자연스럽게 사라진다.
    research = []
    for i, target in enumerate(targets):
        task = dict(by_target.get(target) or {"agent": "research", "kind": "monitoring",
                                              "target": target})
        task["id"], task["status"] = f"task-{i}", "pending"
        research.append(task)
    # 3) 모니터링 외 task(예: analysis)는 건드리지 않고 뒤에 붙인다
    others = [t for t in tasks
              if not (t.get("agent") == "research" and t.get("kind") == "monitoring")]
    return research + others
```

**현재 `agent/nodes/routing_nodes.py` 48~83줄 (`plan_node`)**

```python
@traceable(name="plan_node")
async def plan_node(state: AgentState, deps: SupervisorDeps) -> dict:
    """Wave 4 — Plan/Task 분해. Wave 2의 MCP Prompt가 표준 절차를 깔아준다.

    조사 대상은 모델이 아니라 코드(targets.resolve_targets)가 먼저 정한다 — 대상을
    정할 수 없으면(미등록·미지정) 모델/MCP를 부르지 않고 되묻기로 넘어간다.
    resource와 마찬가지로 이름을 어느 서버가 들고 있는지 미리 가정하지 않고,
    find_prompt()로 연결된 서버들을 먼저 조회해 찾은 뒤에만 get_prompt를 보낸다."""
    res = resolve_targets(state["query"], state.get("history"), deps.known_systems)
    resolved = {"type": "TargetsResolved", "targets": res.targets,
                "unregistered": res.unregistered, "source": res.source}
    if not res.targets:
        return {"clarify": True, "unregistered": res.unregistered,
                "target_source": res.source, "events": state["events"] + [resolved]}

    prompt_server = await deps.mcp.find_prompt("incident_analysis_prompt")
    procedure = await deps.mcp.get_prompt(
        "incident_analysis_prompt",
        {"system_name": res.targets[0], "symptom": state["query"]},
        server=prompt_server,
    )
    # [C11] plan()도 동기 HTTP 호출 → 스레드로 분리 (Before: deps.fast_llm.plan(...) 직접 호출)
    result, usage = await asyncio.to_thread(deps.fast_llm.plan, state["query"], procedure)
    tasks = apply_targets(result["tasks"], res.targets)
    targets = [t["target"] for t in tasks
               if t["agent"] == "research" and t.get("target")]
    # [C12] 분석 실행 여부는 모델 의견 + 코드 규칙(대상 2개 이상)으로 결정한다.
    # Before: "needs_analysis": result["needs_analysis"]  (모델 값을 그대로 사용)
    needs_analysis = decide_needs_analysis(result["needs_analysis"], res.targets)
    event = {"type": "PlanCreated", "task_count": len(tasks), "targets": targets,
             "needs_analysis_model": result["needs_analysis"],
             "needs_analysis": needs_analysis}
    return {"tasks": tasks, "needs_analysis": needs_analysis,
            "clarify": False, "unregistered": res.unregistered,
            "target_source": res.source, "cost_usd": _cost(state, usage),
            "events": state["events"] + [resolved, event]}
```

    """조사 대상을 정할 수 없을 때 — 가정하지 않고 사용자에게 되묻는다 (모델 호출 없음)."""

## 5. 동작 원리 — 코드 읽는 순서
`resolve_targets`는 위에서부터 먼저 해당하는 규칙을 적용한다.

1. 질문에 **등록된 시스템**이 있으면 전부 조사 대상 (B6 해결) → `source="query"`
2. 등록 안 된 이름(`xxx-service` 모양)만 있으면 **대체하지 않고** 조회 불가로 처리 (B2 해결) → 되묻기
3. 시스템이 없지만 이전 사용자 질문에 있으면 그 시스템 (B7 해결) → `source="history"`, 답변 끝에 "이전 대화의 ○○ 기준" 표시
4. 아무것도 없으면 **가정하지 않고** 되묻기 (B3 해결)

`plan_node`는 이 결과가 비어 있으면 `clarify=True`를 반환하고, 그래프는 `plan → clarify → END`로 간다. 대상이 있으면 모델이 만든 계획을 `apply_targets`로 **대상과 일치하게 고친다**(빠진 시스템 추가, 대체된 시스템 제거).

## 9. 한계·트레이드오프
- 시스템이 지정되지 않았을 때 되묻는 방식은 사용자가 한 번 더 입력해야 하는 **UX 비용**이 있다. 로그인 지연처럼 유력한 후보가 있어도 조사를 바로 시작하지 못한다. 대신 확인되지 않은 대상을 확정된 것처럼 제시하지 않는다.
- 시스템 이름 판별은 정규식(`xxx-service`, `xxx-숫자`)이라 다른 이름 규칙은 인식하지 못한다.
- 이력 기반 결정은 "가장 최근 사용자 질문의 첫 시스템"만 쓴다(여러 시스템을 말한 뒤 "그 시스템"은 모호).
