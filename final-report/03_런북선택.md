# 단계 3 — 런북 선택: 근거 없으면 고르지 않기

> 변경 기록 번호: C6 · 전체 기록은 `과제1_코드변경기록.md` · 목차는 [README](README.md)

## 1. 문제 — 무엇이, 왜, 어떤 영향이 있었나
**현상(B1·B5)**: 정상(healthy, 알림 0건)인 `web-01`에 `db-down` 런북이 선택되어 답변에 "필요 시 failover 전환", "DB 관련 점검"이 섞였다.

**원인**: `_classify_incident_type`이 알림 키워드가 하나도 안 맞으면 마지막에 `return "db-down"`으로 폴백했다.
**영향**: 정상 시스템에 엉뚱한 위험 조치를 안내한다. 불필요한 런북 조회로 시간·비용도 늘어난다.

## 2. 바꾼 파일과 이유
| 파일 | 변경 | 이유 |
|---|---|---|
| `agent/incident_rules.py` (신규) | 규칙 표 + `classify_incident_type` (근거 없으면 `None`) | 폴백 제거, 규칙을 순수 함수로 분리 |
| `agent/nodes/research_nodes.py` `replan_check_node` | `None`이면 런북 조회 없이 "런북 근거 없음" 이벤트 | 근거가 없는 런북을 조회하지 않음 |
| `agent/graph.py` | `_INCIDENT_TYPE_RULES`, `_classify_incident_type` 삭제 | 중복·위치 정리 |

**현재 `agent/incident_rules.py` 26~40줄 (`classify_incident_type`)**

```python
def classify_incident_type(collected: list[dict]) -> str | None:
    """수집 결과에서 증상 키워드를 찾아 runbook 종류를 반환. 근거가 없으면 None."""
    # 1) monitoring 결과만 골라 "상태 + 알림 문구들"을 한 줄의 소문자 문자열로 합친다.
    #    예: "degraded cpu 91% (threshold 80%) payments-service-3 instance responding slow"
    text = " ".join(
        f"{c['data'].get('status', '')} " + " ".join(c["data"].get("alerts", []))
        for c in collected if c.get("source") == "monitoring"
    ).lower()
    # 2) 규칙을 순서대로 훑어 처음 맞는 키워드의 런북을 돌려준다.
    for keyword, incident_type in INCIDENT_TYPE_RULES:
        if keyword in text:
            return incident_type
    # 3) 하나도 안 맞으면 None. Before: 여기서 "db-down"을 돌려줘 정상 시스템에도
    #    DB 장애 런북이 붙었다. After: "근거 없음"을 그대로 알린다 (replan_check가 런북 조회를 건너뜀).
    return None
```

**현재 `agent/nodes/research_nodes.py` 94~112줄 (`replan_check_node`)**

```python
@traceable(name="replan_check_node")
async def replan_check_node(state: AgentState, deps: SupervisorDeps) -> dict:
    """Wave 7 — 1차 수집 결과 평가. runbook이 없으면 gap task만 추가해 재조사."""
    has_runbook = any(c["source"] == "runbook" for c in state.get("collected", []))
    rounds = state.get("replan_rounds", 0)
    if has_runbook or rounds >= 1:
        verdict = {"type": "ReplanCheck", "round": rounds, "is_sufficient": True}
        return {"events": state["events"] + [verdict]}
    incident_type = classify_incident_type(state.get("collected", []))
    if incident_type is None:   # 증상 근거가 없으면(정상 시스템 등) 엉뚱한 런북을 붙이지 않는다
        verdict = {"type": "ReplanCheck", "round": rounds, "is_sufficient": True,
                   "reason": "런북 근거 없음"}
        return {"events": state["events"] + [verdict]}
    gap_task = {"id": "task-gap-runbook", "agent": "research", "kind": "runbook",
                "target": incident_type, "status": "pending"}
    verdict = {"type": "ReplanCheck", "round": rounds, "is_sufficient": False,
               "gap_task": gap_task["id"], "target": incident_type}
    return {"tasks": state["tasks"] + [gap_task], "replan_rounds": rounds + 1,
            "events": state["events"] + [verdict]}
```

## 5. 동작 원리 — 코드 읽는 순서
1. 수집된 모니터링 결과에서 `상태 + 알림 문구`를 한 줄로 합쳐 소문자로 만든다.
2. 규칙 표를 위에서부터 훑어 처음 맞는 키워드의 런북을 고른다(예: `cpu` → `cpu-spike`).
3. 하나도 안 맞으면 **`None`** — Before에는 여기서 `db-down`을 돌려줬다.
4. `replan_check_node`는 `None`이면 `ReplanCheck(reason="런북 근거 없음")`만 남기고 런북 조회를 건너뛴다.

- 키워드 규칙이라 알림 문구가 규칙 표에 없는 표현이면 런북을 못 고른다(근거 없음으로 처리됨 — 안전한 쪽).
