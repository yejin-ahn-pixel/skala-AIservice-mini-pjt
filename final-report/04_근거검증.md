# 단계 4 — 근거 검증: 형식만 보던 검증을 사실 대조로

> 변경 기록 번호: C7 · 전체 기록은 `과제1_코드변경기록.md` · 목차는 [README](README.md)

## 1. 문제 — 무엇이, 왜, 어떤 영향이 있었나
**현상(B4)**: `payments-service 결제 응답 지연을 진단해주세요`의 답변에 "최근 배포/트래픽 변화 없음. 반복 호출 또는 배치 작업 패턴 없음"이 있었는데, 수집한 모니터링 데이터에는 이런 조사 결과가 없다. 런북의 "확인한다"는 **지시문**을 모델이 "없음"이라는 **조사 결과**로 바꿔 쓴 것이다. 그런데도 검증은 1회 합격이었다.
**현상(B6)**: 조사한 web-01이 답변에 한 번도 나오지 않았다.

**원인**: `validate_node`가 `len(draft) >= 30 and "1)" in draft`만 검사했다(형식만).
**영향**: 근거 없는 진단도 항상 통과한다(검증이 사실상 없음).

## 2. 바꾼 파일과 이유
| 파일 | 변경 | 이유 |
|---|---|---|
| `agent/verifier.py` (신규) | `find_issues`: ① 수치 대조 ② 조사하지 않은 시스템 언급 ③ 조사한 시스템 누락 ④ 근거 없는 원인 서술 | 코드로 확인 가능한 근거 검사 |
| `agent/nodes/answer_nodes.py` | `validate_node`에 근거 검사 연결, 3회까지 재작성, 그래도 불합격이면 경고와 함께 통과, `finalize_node`가 경고 표시 | 조용한 통과 방지 |
| `ask.py` | "검증 사유" 줄 | 캡처에서 불합격 사유가 보이도록(도구) |
| `tests/test_verifier.py`, `tests/test_validate_node.py` | 검증 규칙·재작성 루프 테스트, **개선 전 B4/B6 답변 재현 테스트** | 실모델이 항상 지어내지는 않으므로 재현 문장으로 효과 증명 |

## 3. Before 코드 (개선 전 원본)

**원본 `agent/graph.py` 274~288줄 (`validate_node`)**

```python
@traceable(name="validate_node")
async def validate_node(state: AgentState, deps: SupervisorDeps) -> dict:
    """Wave 8 — 코드 기준 검증: 30자 이상 + 절차 번호 포함이어야 합격."""
    draft = state["draft"]
    attempts = state.get("validation_attempts", 0) + 1
    ok = len(draft) >= 30 and "1)" in draft
    verdict = "합격" if ok else "불합격"
    if not ok and attempts >= 3:   # 실모델 무한 재작성 방지 — 최대 3회 후 통과 처리
        ok, verdict = True, "합격(최대 시도 도달 — 통과 처리)"
    feedback = None if ok else (
        f"응답이 너무 짧습니다({len(draft)}자, 최소 30자). 절차를 1) 2) 3) 번호로 "
        f"구체적으로 설명하세요.")
    event = {"type": "Validation", "attempt": attempts, "verdict": verdict}
    return {"validation_attempts": attempts, "validation_feedback": feedback,
            "events": state["events"] + [event]}
```

## 4. After 코드 (현재)

**현재 `agent/verifier.py` 97~113줄 (`find_issues`)**

```python
def find_issues(draft: str, query: str, collected: list[dict]) -> list[str]:
    """초안이 수집된 사실에 근거하지 않는 부분을 사람이 읽을 문장 목록으로 반환."""
    facts, monitoring = _facts_text(collected), _monitoring_text(collected)
    issues = []
    # 네 가지 검사를 차례로 수행한다. 하나라도 걸리면 issues에 사유가 쌓이고,
    # validate_node가 이를 근거로 write_node에 재작성을 요청한다(최대 3회).
    # ① 수치  ② 시스템명  ③ 조사한 시스템 누락  ④ 근거 없는 원인 서술
    if nums := _unsupported_numbers(draft, facts):
        issues.append(f"수집된 데이터에 없는 수치: {', '.join(nums)}")
    if names := _unsupported_systems(draft, query, facts):
        issues.append(f"조사하지 않은 시스템 언급: {', '.join(names)}")
    for system in investigated_systems(collected):
        if system.lower() not in draft.lower():
            issues.append(f"조사한 시스템 {system}에 대한 내용이 답변에 없음")
    if claims := _unsupported_claims(draft, monitoring):
        issues.append(f"모니터링 데이터에 근거 없는 조사 결과 서술: {', '.join(claims)}")
    return issues
```

**현재 `agent/nodes/answer_nodes.py` 30~56줄 (`validate_node`)**

```python
@traceable(name="validate_node")
async def validate_node(state: AgentState, deps: SupervisorDeps) -> dict:
    """Wave 8 — 코드 기준 검증: 형식(30자 이상 + 절차 번호) + 근거 검사(verifier).

    근거 검사: 수치·시스템명이 수집된 사실에 있는지, 조사한 시스템이 답변에 모두 있는지,
    모니터링에 없는 '조사 결과 서술'이 없는지. 3회까지 반려·재작성하고, 그래도 불합격이면
    조용히 통과시키지 않고 답변 끝에 경고(validation_warning)를 붙인다."""
    draft = state["draft"]
    attempts = state.get("validation_attempts", 0) + 1   # 이번이 몇 번째 검증인지
    # ① 형식 검사 (Before에는 이것뿐이었다): 30자 이상 + 번호 절차 "1)" 포함
    format_ok = len(draft) >= 30 and "1)" in draft
    # ② 근거 검사 (C7에서 추가): 수치·시스템명·조사 누락·지어낸 원인을 수집 데이터와 대조
    issues = find_issues(draft, state["query"], state.get("collected", []))
    ok = format_ok and not issues       # 둘 다 통과해야 합격
    verdict = "합격" if ok else "불합격"
    warning = None
    if not ok and attempts >= 3:   # 실모델 무한 재작성 방지 — 최대 3회 후 경고와 함께 통과
        ok, verdict = True, "합격(최대 시도 도달 — 경고 표시)"
        warning = "; ".join(issues) or "형식 기준 미충족"
    # 불합격이면 사유를 문장으로 만들어 돌려준다 → 그래프가 write_node로 되돌아가 재작성
    # (_after_validate: feedback이 None이면 finalize, 아니면 write)
    feedback = None if ok else build_feedback(draft, format_ok, issues)
    event = {"type": "Validation", "attempt": attempts, "verdict": verdict}
    if issues:
        event["issues"] = issues
    return {"validation_attempts": attempts, "validation_feedback": feedback,
            "validation_warning": warning, "events": state["events"] + [event]}
```

## 5. 동작 원리 — 코드 읽는 순서
1. 초안에서 `55.1%`, `2.4s`처럼 **단위 붙은 수치**를 뽑아, 수집된 데이터의 숫자와 오차 범위(%는 ±1, s는 ±0.05) 안에서 대조한다.
2. 초안의 시스템 이름이 질문 또는 수집 데이터에 있는지 본다.
3. 조사에 성공한 시스템 이름이 초안에 모두 등장하는지 본다.
4. "~없음/~확인됨" 같은 **단정 문장**에 원인 후보 단어(배포·트래픽·배치 …)가 있는데 모니터링 데이터에 없으면 위반. 단, "수집된 데이터에 없음"처럼 솔직히 밝히는 문장은 정상.
5. 사유가 있으면 `build_feedback`이 재작성 지시문을 만들고 그래프가 `write_node`로 돌아간다(최대 3회, 이후 경고 표시).

## 9. 한계·트레이드오프
- 규칙·사전 기반이라 목록에 없는 표현의 지어내기는 못 잡는다. LLM-as-judge는 큰 모델을 한 번 더 불러 지연·비용이 늘어 쓰지 않았다.
- 재작성이 일어나면 응답이 약 30~35초 더 걸린다(8b 모델 재호출).
- 실모델에서 검증이 걸러낸 장면은 아직 캡처하지 못했다 → 보고서에는 "발생했을 때를 막는 장치 + 재현 테스트"로 정직하게 서술한다.
