# 단계 1 — 라우팅 보강: 운영 질문이 chat으로 빠지지 않게

> 변경 기록 번호: C1, C5 · 전체 기록은 `과제1_코드변경기록.md` · 목차는 [README](README.md)

## 1. 문제 — 무엇이, 왜, 어떤 영향이 있었나
**현상(B1)**: `web-01 상태 진단해줘`를 보냈더니 소형 분류 모델(qwen3:0.6b)이 `chat`으로 분류했다. chat 경로는 모니터링을 조회하지 않아서, 답변이 "진행 중입니다"처럼 **조회 없이 지어낸 말**이었다(실제 상태는 healthy).

**원인**: `route_node`가 모델의 분류 결과를 그대로 믿었다. 0.6b 모델은 명백한 운영 질문도 chat으로 분류하는 경우가 있다.

**영향**: 가장 기본적인 질문에서 근거 없는 답변이 나온다. 이후 단계(조사·검증)가 아예 실행되지 않는다.

**후속 질문도 같은 문제(B7)**: "그 시스템 메모리는 어때?"처럼 시스템 이름이 없는 후속 질문은 더 쉽게 chat으로 빠진다.

## 2. 바꾼 파일과 이유
| 파일 | 변경 | 이유 |
|---|---|---|
| `agent/routing.py` (신규) | `should_force_incident` | "시스템 이름 + 운영 키워드"면 incident로 보정하는 순수 함수 |
| `agent/graph.py` → 현재 `agent/nodes/routing_nodes.py`의 `route_node` | 모델 결과가 chat이어도 위 함수가 True면 incident로 변경, 이벤트에 `overridden_from: chat` 기록 | 코드로 검증 가능한 판단은 코드가 내린다(gate_node와 같은 원칙) |
| `tests/test_routing.py`, `tests/test_route_node.py` (신규) | 보정 규칙·노드 단위 테스트 | 모델 없이 규칙을 확인 |

## 4. After 코드 (현재)

**현재 `agent/routing.py` 25~44줄 (`should_force_incident`)**

```python
def should_force_incident(query: str, known_systems: set[str],
                          history: list[dict] | None = None) -> bool:
    """모델이 chat이라고 했어도 incident로 바꿔야 하는 질문인가.

    '시스템 이름 + 운영 키워드'가 함께 있을 때만 True — 인사·잡담이 incident로
    잘못 넘어가지 않도록 두 조건을 모두 요구한다. 시스템 이름 대신 "그 시스템" 같은
    지시어가 있고 이전 대화에 시스템이 있으면 후속 질문으로 본다."""
    # ① 운영 키워드가 하나도 없으면 인사·잡담이다 → 모델 판단(chat)을 그대로 둔다.
    #    예: "안녕하세요" → False
    if not OPS_KEYWORDS.search(query):
        return False
    # ② 키워드가 있고, 질문에 시스템 이름도 있으면 운영 질문이다 → incident로 바꾼다.
    #    예: "web-01 상태 진단해줘"(상태+web-01) → True  (개선 전 B1: 모델이 chat으로 분류)
    if mentions_system(query, known_systems):
        return True
    # ③ 시스템 이름은 없지만 "그 시스템" 같은 지시어가 있고, 이전 대화에 시스템이 있으면
    #    후속 질문으로 본다. 예: (앞 질문: payments-service) "그 시스템 메모리는 어때?" → True
    #    이전 대화에 시스템이 없으면 False (되묻기는 plan 단계에서 처리).
    return bool(DEICTIC.search(query)) and \
        last_system_from_history(history, known_systems) is not None
```

**현재 `agent/nodes/routing_nodes.py` 12~29줄 (`route_node`)**

```python
@traceable(name="route_node")
async def route_node(state: AgentState, deps: SupervisorDeps) -> dict:
    """Wave 5 — 모든 쿼리가 무거운 파이프라인을 탈 필요는 없다."""
    # [C11] route()는 동기 함수(내부에서 HTTP 호출). async 노드에서 그대로 부르면 응답을 기다리는
    # 동안 이벤트 루프 전체가 멈춰 /health 등 다른 요청이 같이 지연된다.
    # Before: result, usage = deps.fast_llm.route(state["query"])
    # After : to_thread로 별도 스레드에서 실행 → 기다리는 동안 이벤트 루프는 다른 요청을 처리
    result, usage = await asyncio.to_thread(deps.fast_llm.route, state["query"])
    route = result["route"]
    event = {"type": "RouteDecided", "route": route}
    # 소형 모델이 운영 질문을 chat으로 오분류하면 조회 없이 답이 지어진다 → 코드가 보정
    if route == "chat" and should_force_incident(state["query"], deps.known_systems,
                                         state.get("history")):
        route = "incident"
        event = {"type": "RouteDecided", "route": route, "overridden_from": "chat"}
    return {"route": route, "needs_analysis": result["needs_analysis"],
            "cost_usd": _cost(state, usage),
            "events": state.get("events", []) + [event]}
```

## 5. 동작 원리 — 코드 읽는 순서
1. 모델이 `route`를 판단한다(바뀌지 않음).
2. 모델이 chat이라고 했을 때만 `should_force_incident`를 호출한다.
3. 이 함수는 ① 운영 키워드(상태·진단·지연 …)가 있는가 → ② 시스템 이름이 있는가(등록된 이름 또는 `xxx-service` 모양) → ③ 없으면 "그 시스템" 같은 지시어 + 이전 대화에 시스템이 있는가 순서로 본다.
4. True면 route를 `incident`로 바꾸고, 바꿨다는 사실을 이벤트(`overridden_from`)로 남긴다.
5. 인사·잡담은 키워드가 없어서 그대로 chat이다(오탐 방지를 위해 **두 조건을 모두** 요구).
